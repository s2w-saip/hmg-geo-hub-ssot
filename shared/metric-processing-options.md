# 지표 가공 구조

분석팀은 추출만 하고, 서비스(BFF)가 지표를 정의하고 계산한다.

## 1. 단계와 담당

| 단계 | 하는 일 | 담당 |
|---|---|---|
| 수집 | AI 엔진에 질의, 응답 수신 | 앤써 |
| 분석 | 응답에서 정보 추출 (AI 모델) | 신민철, 박보규 |
| 가공 | 추출 결과를 정의대로 집계해 지표 계산 | 서비스: 김태호 (BFF) |
| 서비스 제공 | 화면, 지표 API | 서비스: 김태호 |
| 데이터 파이프라인 | 분석 입력 준비, OBT 스냅샷 적재·운영 반영 | 이시형, 김혜민 |

## 2. 데이터 흐름

`[ ]` 안은 담당이다.

1. 입력(프롬프트, 측정 설정) → 수집 서버 → 응답 원문(Bronze) `[앤써]`
2. 응답 원문 → 분석 입력 준비 `[파이프라인]`: 수집 데이터를 분석에 쓸 수 있게 정리한다.
3. 분석 입력 준비 → AI 모델 추출 `[분석팀]`
4. AI 모델 추출 → OBT(Silver) `[파이프라인]`: 분석팀의 추출 결과를 스냅샷으로 적재하고 운영에 반영한다.
5. OBT 운영 스냅샷 → BFF 지표 계산 ↔ 사전 집계 테이블(Gold) `[서비스]`
6. BFF 지표 계산 → 화면 조립·API → 웹 화면, 지표 API `[서비스]`

지표 변경(새 지표, 필터, 분모)은 서비스 안에서 끝난다.

## 3. 계층과 계약

계층마다 저장소는 하나다. OBT(One Big Table)는 한 테이블에 컬럼을 많이 두는 방식일 뿐이며, 데이터 정규화는 한다. 한 컬럼에 값이 여러 개 들어가야 하면 jsonb로 넣는다(Silver만 해당).

| 계층 | 저장소 | 담는 것 | 쓰기 | 데이터 방향 |
|---|---|---|---|---|
| Bronze | 응답 원문 | 답변 키, 프롬프트, 엔진, 국가, 언어, 측정 시각, 본문, 인용 원문 | 앤써 | 앤써 → 분석 (계약 1) |
| Silver | 추출 결과 OBT | 답변 1건 = 1행, 추출 컬럼만, 추출 규칙 버전, 스냅샷 ID, 스냅샷 상태 | 파이프라인 | 분석 → 서비스 (계약 2) |
| Gold | 사전 집계 테이블 | 집계 비용이 큰 지표의 회차·국가·엔진·브랜드별 값, 스냅샷 ID·지표 정의 버전 | 서비스 | 서비스 내부 (계약 아님) |

## 4. 추출과 가공의 경계

| 구분 | 추출 (분석팀) | 가공 (BFF) |
|---|---|---|
| 정의 | 응답에서 읽어 낸 정보와 분류 | 추출 결과를 집계하는 규칙 |
| 예 | 엔티티→브랜드 매핑, 감성, 언급 유형, 언급 순위·첫 언급 위치, 인용 URL·출처 분류 | 분모 조건, 자사 여부 판정, 대표 답변 선정, 집계 기간(회차·기간), 계산식 |
| 변경 시점 | 모델이 바뀔 때 | 화면 요구가 바뀔 때 |

## 5. 운영 반영

파이프라인은 회차마다 OBT를 새 스냅샷으로 적재한다. 운영 반영은 그 스냅샷을 `public`(운영 중)으로 바꾸는 일이고, 데이터 복사는 없다.

1. 파이프라인이 새 스냅샷을 적재한다(`loading`, 임시 저장). 화면은 이전 운영 스냅샷을 계속 보여 준다.
2. 파이프라인이 행 수, 필수 컬럼, 키 중복을 검증하고 `ready`로 바꾼 뒤 매니페스트(적재 기록)에 적는다.
3. 파이프라인이 한 트랜잭션으로 운영 스냅샷 포인터를 바꾼다(`public`). 이전 스냅샷은 `retired`가 되고 1~2개만 보관한다.
4. 서비스는 매니페스트로 새 스냅샷을 확인하고 사전 집계를 갱신한 뒤 캐시를 비운다.
5. 사전 집계가 늦거나 실패하면 BFF가 조회 시점에 Silver에서 집계한다. 느리지만 값은 맞다.
6. 롤백할 때는 포인터를 `retired` 스냅샷으로 돌린다.

| 구성 요소 | 쓰기 | 읽기 |
|---|---|---|
| 매니페스트: 회차, 스냅샷 ID, 행 수, 추출 규칙 버전, 상태 | 파이프라인 | 서비스 |
| 운영 스냅샷 포인터 (회차마다 한 행) | 파이프라인 | BFF |
| Silver 조회용 인덱스 | 서비스 (인덱스 생성 권한만) | BFF |

**책임.** 적재가 빠짐없이 됐는지는 파이프라인, 추출 내용은 분석팀, 지표는 서비스가 책임진다. 문제가 생기면 매니페스트와 사전 집계 테이블에 남은 스냅샷 ID·지표 정의 버전으로 어느 단계 문제인지 찾는다.

## 6. 지표 계산 방식

- **조회 시점 집계:** BFF가 OBT 운영 스냅샷에서 집계하고 캐시한다. 최근 1~4회차 조회가 여기에 해당한다.
- **사전 집계:** 집계 비용이 큰 지표만 회차 단위로 미리 계산해 둔다. 예: 기간 전체 출처 도메인 순위

## 7. 운영 원칙

1. **OBT 계약을 고정한다.** 컬럼, 의미, 스냅샷 ID를 문서로 두고, 바꿀 때는 미리 알린다.
2. **지표는 BFF로만 내보낸다.** 지표 API를 포함해 모든 소비자가 BFF를 거친다.
3. **읽는 스냅샷을 고정한다.** BFF는 운영 스냅샷만 읽고, 재분석 결과는 운영 반영 뒤에만 화면에 나온다.
4. **지표 정의는 코드와 테스트로 남긴다.** 정의 변경은 분석팀도 리뷰한다.

값은 예시다.

### 응답 원문 (Bronze, 답변 1건)

| 항목 | 값 |
|---|---|
| answer_key | `8812031` |
| 프롬프트 | best 3-row SUV for families |
| 엔진 | ChatGPT |
| 국가 | US |
| 언어 | en |
| 측정 시각 | 2026-10-05 09:12 |
| 본문 | "1. **Kia Telluride** – roomy, top safety picks … 2. **Hyundai Palisade** … 3. Toyota Grand Highlander … [1][2][3]" |
| 인용 원문 | [1] kia.com/us/telluride, [2] caranddriver.com/…, [3] edmunds.com/… |

### 추출 결과 OBT (Silver, 답변 1건 = 1행)

| 항목 | 값 |
|---|---|
| answer_key | `8812031` |
| 프롬프트 | best 3-row SUV … |
| 엔진 | ChatGPT |
| 국가 | US |
| 회차 | 2026-10-05 |
| 언급 브랜드 (jsonb) | `[{"브랜드":"Kia","순위":1,"감성":"긍정","유형":"추천"}, {"브랜드":"Hyundai","순위":2,"감성":"긍정","유형":"비교"}, {"브랜드":"Toyota","순위":3,"감성":"중립","유형":"언급"}]` |
| 인용 (jsonb) | `[{"url":"kia.com/us/telluride","출처 분류":"공식 HMG"}, {"url":"caranddriver.com/…","출처 분류":"자동차 미디어"}, {"url":"edmunds.com/…","출처 분류":"리뷰·비교"}]` |
| … | 추출 컬럼이 더 있다. |
