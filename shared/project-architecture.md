# 지표 가공 구조

분석팀은 추출만 하고, 서비스(BFF)가 지표를 정의하고 계산한다.

## 1. 단계와 담당

| 단계 | 하는 일 | 담당 |
|---|---|---|
| 수집 | AI 엔진에 질의, 응답 수신 | 앤써 |
| 분석 | 응답에서 정보 추출 (AI 모델) | 신민철, 박보규 |
| 가공 | 추출 결과를 정의대로 집계해 지표 계산 | 서비스: 김태호 (BFF) |
| 서비스 제공 | 화면, 지표 API | 서비스: 김태호 |
| 데이터 파이프라인 | 분석 입력 준비, OBT 스냅샷 적재·운영 반영 | 이시형, 김혜민 |

## 2. 데이터 흐름

`[ ]` 안은 담당이다.

1. 프롬프트·기준정보 원본(서비스 DB) → 프롬프트·기준정보 API `[서비스]`
2. 프롬프트·기준정보 API → 입력(프롬프트, 측정 설정) → 수집 서버 → 응답 원문(Bronze) `[앤써]`
3. 응답 원문 → 분석 입력 준비(임시 DB) `[파이프라인]`: 데이터 수급 안정성을 위해 Bronze를 통째로 복사해 둔다.
4. 분석 입력 준비, 프롬프트·기준정보 API(분석 기준정보) → AI 모델 추출 `[분석팀]`
5. AI 모델 추출 → OBT(Silver) `[파이프라인]`: 분석팀의 추출 결과를 스냅샷으로 적재하고 운영에 반영한다.
6. OBT 운영 스냅샷 → BFF 지표 계산 ↔ 사전 집계 테이블(Gold), 캐시 DB `[서비스]`
7. BFF 지표 계산 → 화면 조립·API → 웹 화면, 지표 API `[서비스]`

지표 변경(새 지표, 필터, 분모)은 서비스 안에서 끝난다.

## 3. 계층과 계약

계층마다 정본 저장소는 하나다. OBT(One Big Table)는 한 테이블에 컬럼을 많이 두는 방식이며, 데이터 정규화는 하지 않는다. 항목마다 컬럼을 따로 두고, 한 컬럼에 값이 여러 개 들어가야 하면 jsonb로 넣는다(Silver만 해당).

| 계층 | 저장소 | 담는 것 | 데이터 생성 주체 | 데이터 관리 담당 | 데이터 방향 |
|---|---|---|---|---|---|
| — | 프롬프트·기준정보 원본 | 프롬프트, 측정 설정, 분석 기준정보 | 서비스 | 서비스 | 서비스 → 앤써 (프롬프트, 측정 설정), 서비스 → 분석 (분석 기준정보). 프롬프트·기준정보 API로 읽음 |
| Bronze | 응답 원문 | 답변 키, 프롬프트, 엔진, 국가, 언어, 측정 시각, 본문, 인용 원문 | 수집 | 수집 | 앤써 → 분석 (계약 1) |
| — | 분석 입력 준비 (임시 DB) | Bronze 전체 사본(데이터 수급 안정용) | 파이프라인 | 파이프라인 | 파이프라인 내부 (정본 아님) |
| Silver | 추출 결과 OBT | 답변 1건 = 1행, 추출 컬럼만, 추출 규칙 버전, 스냅샷 ID, 스냅샷 상태 | 분석 | 파이프라인(주), 분석(부) | 분석 → 서비스 (계약 2) |
| Gold | 사전 집계 테이블 | 필터 없는 초기 화면의 지표 값, 스냅샷 ID·지표 정의 버전 | 서비스 | 서비스 | 서비스 내부 (계약 아님) |
| — | 캐시 DB | 필터 조회 결과(조회 조건별, 다음 회차 운영 반영 전까지) | 서비스 | 서비스 | 서비스 내부 (정본 아님) |

## 4. 추출과 가공의 경계

| 구분 | 추출 (분석팀) | 가공 (BFF) |
|---|---|---|
| 정의 | 응답에서 읽어 낸 정보와 분류 | 추출 결과를 집계하는 규칙 |
| 예 | 엔티티→브랜드 매핑, 감성, 언급 유형, 언급 순위·첫 언급 위치, 인용 URL·출처 분류 | 분모 조건, 자사 여부 판정, 대표 답변 선정, 집계 기간(회차·기간), 계산식 |
| 변경 시점 | 모델이 바뀔 때 | 화면 요구가 바뀔 때 |

## 5. 운영 반영

파이프라인은 회차마다 OBT를 새 스냅샷으로 적재한다. 운영 반영은 그 스냅샷을 `public`(운영 중)으로 바꾸는 일이고, 데이터 복사는 없다.

1. 파이프라인이 새 스냅샷을 적재한다(`loading`, 임시 저장). 화면은 이전 운영 스냅샷을 계속 보여 준다.
2. 파이프라인이 행 수, 필수 컬럼, 키 중복을 검증하고 `ready`로 바꾼 뒤 매니페스트(적재 기록)에 적는다.
3. 파이프라인이 한 트랜잭션으로 운영 스냅샷 포인터를 바꾼다(`public`). 이전 스냅샷은 `retired`가 되고 1~2개만 보관한다.
4. 서비스는 매니페스트로 새 스냅샷을 확인하고 사전 집계를 갱신한 뒤, 캐시 DB에서 이전 스냅샷의 결과를 지운다.
5. 사전 집계가 늦거나 실패하면 그 지표는 보여 주지 않는다.
6. 롤백할 때는 포인터를 `retired` 스냅샷으로 돌린다.

| 구성 요소 | 쓰기 | 읽기 |
|---|---|---|
| 매니페스트: 회차, 스냅샷 ID, 행 수, 추출 규칙 버전, 상태 | 파이프라인 | 서비스 |
| 운영 스냅샷 포인터 (회차마다 한 행) | 파이프라인 | BFF |

**책임.** 적재가 빠짐없이 됐는지는 파이프라인, 추출 내용은 분석팀, 지표는 서비스가 책임진다. 문제가 생기면 매니페스트와 사전 집계 테이블에 남은 스냅샷 ID·지표 정의 버전으로 어느 단계 문제인지 찾는다.

## 6. 지표 계산 방식

- **사전 집계:** 필터 없는 초기 화면 값은 회차마다 미리 전부 계산해 Gold에 둔다.
- **조회 시점 집계:** 필터를 건 조회는 BFF가 OBT 운영 스냅샷에서 전체를 센다. 기간 제한이 없어 첫 조회는 오래 걸릴 수 있다. 결과는 조회 조건별로 캐시 DB에 저장해 같은 회차 안에서 다시 쓴다. 구현 기준: [service/cache-db.md](../service/cache-db.md)

## 7. 운영 원칙

1. **OBT 계약을 고정한다.** 컬럼, 의미, 스냅샷 ID를 문서로 두고, 바꿀 때는 미리 알린다.
2. **지표는 BFF로만 내보낸다.** 지표 API를 포함해 모든 소비자가 BFF를 거친다.
3. **읽는 스냅샷을 고정한다.** BFF는 운영 스냅샷만 읽고, 재분석 결과는 운영 반영 뒤에만 화면에 나온다.
4. **지표 정의는 코드와 테스트로 남긴다.** 정의 변경은 분석팀도 리뷰한다.
5. **OBT 파티션·인덱스는 파이프라인이 관리한다.** OBT를 회차·스냅샷 단위로 골라 읽을 수 있게 해서, 조회 범위가 같으면 데이터가 쌓여도 조회 시간이 늘지 않게 한다.
